# 平台级自动部署与修复（2026-10-21）

新建项目、更新部署和明确的对话部署指令，默认进入同一条流程：固定源码提交 → 识别运行方式 → 校验方案 → 自动构建 → 检查服务 → 失败后交给 DeepSeek 诊断、修正和重新部署。

## 已实现

- 支持直接静态发布、安装依赖/构建后静态发布、Nixpacks 服务和 Dockerfile 服务。后端项目不再套用 `index.html` 校验。
- 构建失败和发布后的端点检查失败均会自动进入修复。准备源码、配置应用阶段的异常也会交给 AI 诊断。
- DeepSeek 可以调整安装、构建、启动命令、目录、端口、健康端点、内存额度（256–1536 MB），并按固定提交补读源码。
- 非标准项目可生成应用目录 `.song-deploy/` 下的 `Dockerfile`、`start.sh`、`nginx.conf`。生成内容进入单独的 Git 构建快照，保留原始源码提交和生成文件摘要；不改写 GitHub 仓库，不覆盖上游文件。派生提交复用已有 Git 对象，不再次检出或复制整个大仓库。Dockerfile 最终镜像直接运行，不叠加 Nginx 静态包装层。
- 修复时提供构建日志及可读取的运行日志，标明运行日志可能来自上次成功版本。先读取环境变量用于脱敏；存在隐藏变量或无法读取环境变量时，不向模型转发原始日志。
- 每次操作最多自动修复 4 轮，每轮最多 4 次模型交互（用于补读文件、修正无效输出）。重复失败的方案会被拒绝；原方案的瞬时故障重试最多一次。手动继续会归档上一轮记录，重新开始额度。
- 对话中明确要求“部署”“更新部署”“修复问题”可直接提交后台任务；删除和访问权限仍使用现有明确操作入口。
- “暂停自动处理”通过独立控制文件阻止下一次构建，避免被旧工作线程状态覆盖。已提交的引擎构建仍会执行完毕。
- 服务重启后恢复已提交部署的监控和未完成的识别/修复；无法确定是否提交成功的任务会明确提示，避免创建重复构建。
- 已有项目启用相同自动流程，本次升级不重新部署这些项目。

## 真实边界

这是公开 GitHub 仓库、单个 Web 应用的自动部署执行器，不保证任意仓库都能在当前服务器运行。私有仓库授权、业务密钥、数据库/持久卷配置、多服务编排、GPU 和超出机器容量的资源需求仍有执行能力缺口；AI 必须说明具体缺什么，不能虚构凭据或用假成功页面绕过验证。Git LFS、子模块、符号链接和超大截断文件树仍受源码快照实现限制。

当前自动修复发生在一次部署流程内，不是部署成功后的持续运行故障监控。健康验证检查真实 HTTP 端点，不等于完整业务验收。模型不可操作宿主机 Shell、Docker socket 或任意引擎 API；命令通过现有隔离构建执行器运行。

## 验证

- 后端回归：`deployment/agent/test_autonomous.py` 与既有测试，涵盖自动启动、失败修复、重复方案、重启恢复、暂停、密钥脱敏、权限校验及真实 Git 派生快照。
- 浏览器回归：`deployment/agent/test_workbench.cjs`，检查操作按钮、自动日志更新、重复提交保护、草稿保留及移动端布局。
- 在线验收结果记录在 `deployment/autonomous-acceptance.json`。测试使用独立临时应用，注入不存在的健康端点，观察真实失败后 DeepSeek 修复和重新部署；不修改原有应用。

在线验收还发现原代理 192 MB 内存限制导致入口握手和 HTTP 超时；已把 `coolify-proxy` 限制调整为 512 MB，并同步持久化 Compose 与 `bootstrap_coolify.py`。调整后公网入口恢复，无需重启代理。

最终验证：85 项后端测试通过，工作台公网浏览器检查无 JavaScript 错误。独立测试应用经历真实构建失败后，由 DeepSeek 自动修复 2 轮并部署成功，生成文件仅在 `.song-deploy/` 内，原始源码文件树保持一致。工作台、Bluey、Greencircle 与测试应用 HTTPS 均返回 200；测试应用已清理。详细历史保留于验收 JSON。
